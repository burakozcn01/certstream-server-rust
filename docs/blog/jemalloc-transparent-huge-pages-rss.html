358 MB resident, 52 MB in use: where the rest went

A service that looked like it was leaking. It wasn't, and the fix was five settings the allocator had been running without.

A Certificate Transparency server I maintain had been sitting at around 130 MB resident for months. I finally got around to profiling it properly, ran it for two hours on my laptop, and watched resident memory climb to 682 MB without ever levelling off.

That looks exactly like a leak. It wasn't one. The allocator was holding everything it should have been holding; the kernel was the one keeping the pages.

What the numbers looked like

The workload is steady and easy to reason about: 45 CT logs polled in parallel, roughly 420 certificates a second parsed and broadcast, one subscriber attached. Nothing accumulates by design. There is a dedup cache with a fifteen minute window, a thousand-entry cache for the REST endpoint, and a broadcast channel that holds a thousand messages. Add it up generously and you get maybe 60 MB.

# two hours, sampled every 30s
  0 min   180 MB
  5 min   423 MB
 27 min   513 MB
 54 min   591 MB
 81 min   679 MB
108 min   682 MB

The curve flattens near the end, which is the shape of something converging rather than leaking. But converging on 682 MB when you can only account for 60 MB is its own problem.

The hypothesis that was wrong

My first guess was the dedup cache. It is the one structure whose size scales with traffic: it holds a SHA-256 per certificate for fifteen minutes, and at 420 certs/s that is roughly 378,000 entries. The configured capacity said 200,000, so I assumed the cap was not being enforced and the map had quietly grown past it.

Half right, and useless. The cap really was not being enforced (a separate bug, since fixed). But 378,000 entries of a 32 byte key, a 16 byte timestamp and hashmap overhead is about 34 MB. Even if the map had doubled, it could not explain a 600 MB gap.

My second guess was the tile and batch buffers. Catch-up pipelines four concurrent fetches per watcher, each response is hundreds of kilobytes of JSON or a compressed tile that expands to a few megabytes, and 45 watchers doing that at once is a lot of transient allocation. Plausible, and also wrong, but it took measurement to know that.

The thing I should have measured first, and didn't, was whether the process was actually holding that memory at all.

Asking the allocator

The server uses jemalloc. jemalloc knows exactly how much memory the application is holding, and it will tell you, but only if something asks. I wired six of its counters into the Prometheus endpoint:

certstream_jemalloc_allocated_bytes   // what the app holds
certstream_jemalloc_active_bytes
certstream_jemalloc_resident_bytes    // pages backed by physical memory
certstream_jemalloc_mapped_bytes
certstream_jemalloc_retained_bytes
certstream_jemalloc_metadata_bytes

One detail that will bite you: jemalloc caches these numbers and only refreshes them when you advance its epoch. Read them without that and you get the values from process start, which looks like a beautifully flat heap.

With the counters live, the picture inverted:

The figures below come from a shorter run on the same host, once the counters were in: minutes rather than hours, so resident memory is at 358 MB on its way up rather than the 682 MB the two hour run ended at. The ratio is what matters and it holds throughout.

MeasureBytes
RSS, as the kernel sees it358 MB
jemalloc resident95 MB
jemalloc allocated, the live heap52 MB

The live heap was 52 MB, right where the arithmetic said it should be. Nothing was leaking. But the allocator only admitted to 95 MB of resident pages while the kernel was charging the process for 358 MB, and that gap is not something jemalloc's own accounting can explain.

Where the memory actually was

/proc/pid/smaps_rollup answers this in one line, and I wish I had looked at it an hour earlier:

Rss:              358240 kB
AnonHugePages:    206848 kB

206 MB of the 358 was transparent huge pages. The host had THP set to always:

$ cat /sys/kernel/mm/transparent_hugepage/enabled
[always] madvise never

In that mode the kernel promotes anonymous mappings into 2 MiB pages wherever it can. jemalloc allocates and frees at 4 KiB granularity, and when it wants to give memory back it does so a page at a time. A 2 MiB huge page with a single 4 KiB object still live in it cannot be returned. Under a workload that churns short-lived buffers across many threads, you end up with a lot of huge pages that are mostly free and entirely unreturnable.

Two other defaults were compounding it. jemalloc sizes its arena count as four times the CPU count, and inside a container that reads the host CPU count, not the cgroup quota: 72 arenas on an 18 core machine, each with its own dirty page pool and its own decay clock, serving a runtime that only has four worker threads. And decay only advances when an arena is touched, so arenas belonging to bursty watcher tasks sat on their dirty pages indefinitely.

The part that convinced me

The same binary runs in production on a Linux box that had been up for twenty hours. I checked it expecting to see the same thing:

$ cat /sys/kernel/mm/transparent_hugepage/enabled
always [madvise] never

$ grep -E '^(Rss|AnonHugePages)' /proc/$pid/smaps_rollup
Rss:              137436 kB
AnonHugePages:         0 kB

Zero huge pages, 137 MB resident, twenty hours of uptime. Same code, same workload, different THP setting. That is when I stopped looking for a leak.

This is also why nobody had reported it. Debian and Ubuntu ship THP in madvise mode, so their users never see it. Docker Desktop's Linux VM, RHEL derivatives and a fair number of cloud images use always, and their users see a process that appears to use four times the memory it does.

The fix

Five settings, embedded in the binary so they apply however it is installed:

thp:never,narenas:4,background_thread:true,dirty_decay_ms:5000,muzzy_decay_ms:5000

thp:never makes jemalloc mark its own mappings MADV_NOHUGEPAGE, which opts the allocator out without touching anything else on the host. narenas:4 matches the runtime's actual thread count instead of the host's core count. background_thread:true gives idle arenas a purger, since the decay timer alone only fires when someone allocates.

In Rust with tikv-jemallocator, the way to ship a default is an exported symbol, remembering that the crate builds jemalloc with a _rjem_ prefix:

#[cfg(all(not(target_env = "msvc"), target_os = "linux"))]
#[used]
#[unsafe(export_name = "_rjem_malloc_conf")]
pub static MALLOC_CONF: &[u8] = b"thp:never,narenas:4,...\0";

Three things worth knowing about that snippet. #[used] is load bearing: nothing in the crate reads the symbol, jemalloc looks it up at startup, and fat LTO will otherwise drop it. The Linux guard matters too, because macOS has no THP and no pthread background thread support, so passing those options there prints two warnings to stderr on every start. And because jemalloc reads the _RJEM_MALLOC_CONF environment variable after the symbol, operators can still override any of it without rebuilding.

What it did

MeasureBeforeAfter
RSS, THP always host358 MB83 MB
RSS, THP madvise host88 MB77 MB
AnonHugePages206 MB6 MB
jemalloc retained116 MB34 MB
Arena metadata11.8 MB4.8 MB
Live heap52 MB49 MB

The live heap did not move, which is the whole point. Nothing about how the program uses memory changed. The pages just started going back.

The madvise host improved too, by about 11 MB, which is the arena and decay settings doing their smaller share of the work.

What I'd tell you to take from this

RSS answers "what is this process being charged for". It does not answer "what is this process holding", and on a machine with THP enabled those two numbers can differ by a factor of four with nothing wrong. If your allocator can report its own live heap, export it next to RSS and put both on the same graph. The gap between them is the diagnosis.

Check /sys/kernel/mm/transparent_hugepage/enabled before you believe a memory graph, especially one from a container on a developer laptop. A bug that only reproduces on always hosts will look intermittent and machine-specific, which is the worst kind of bug to chase.

And if you make an allocator swap, configure it in the same commit. jemalloc had been the global allocator in this project for two releases with no configuration at all, which meant it was running with arena counts derived from whatever machine it landed on and a decay policy that never ran on idle arenas. The swap was the right call; leaving it at defaults quietly undid most of the benefit.

The code is certstream-server-rust, a Certificate Transparency log streaming server. The allocator settings landed in v1.5.5 along with the jemalloc metrics.
