358 MB resident, 52 MB in use: where the rest went

A service that looked like it was leaking. It wasn't, and the fix was five settings the allocator had been running without.

Certificate Transparency logs are append-only records of TLS certificates issued by public CAs. I run a server that reads those logs and streams the certificates to connected clients.

The server had been using around 130 MB of resident memory (RSS) for months. When I finally profiled it over a longer period, RSS kept growing. After two hours it had reached 682 MB and still hadn't levelled off.

The workload shouldn't retain anywhere near that much memory. There is a deduplication cache with a fifteen minute window, a 1,000-entry cache for the REST endpoint, and a broadcast channel holding 1,000 messages. Even with generous estimates, the data the application actually needs to keep around should fit in roughly 60 MB.

So at first this looked like a memory leak.

RSS and the heap are not the same thing

RSS is the amount of physical memory currently mapped into the process. It doesn't tell you how much memory the application is actively using.

This distinction matters with allocators. When an object is freed, the allocator may keep the page that contained it instead of immediately returning that page to the kernel. The page still contributes to RSS even though the allocation itself is gone.

I needed the allocator's view of memory before assuming that the application was retaining objects.

Checking jemalloc

The server uses jemalloc. I added several jemalloc counters to the existing Prometheus endpoint:

certstream_jemalloc_allocated_bytes   // live heap
certstream_jemalloc_active_bytes
certstream_jemalloc_resident_bytes    // physical pages jemalloc accounts for
certstream_jemalloc_mapped_bytes
certstream_jemalloc_retained_bytes
certstream_jemalloc_metadata_bytes

One thing to watch for when collecting these is jemalloc's epoch. The statistics are cached, so the epoch has to be advanced before reading them. Otherwise the values can stay at their startup values and make the heap look completely flat.

After adding the counters, I ran the same workload again. This was a shorter run, so RSS had reached 358 MB rather than the 682 MB from the earlier two-hour test.

MeasureMemory
RSS reported by the kernel358 MB
jemalloc resident95 MB
jemalloc allocated52 MB

The useful number here was allocated: 52 MB.

That was close to what I expected from the application's caches and other live data. The application wasn't holding hundreds of megabytes of objects.

There was still another problem, though. jemalloc accounted for 95 MB of resident memory while the kernel reported 358 MB for the process.

Finding the missing memory

/proc/$pid/smaps_rollup made the difference fairly obvious:

Rss:              358240 kB
AnonHugePages:    206848 kB

About 206 MB of the 358 MB RSS was in transparent huge pages.

The machine was running THP in always mode:

$ cat /sys/kernel/mm/transparent_hugepage/enabled
[always] madvise never

With always, the kernel can promote anonymous memory into 2 MiB huge pages.

That doesn't work particularly well with this workload. The server processes around 420 certificates per second across roughly 100 tasks. Each certificate involves a short-lived buffer of several kilobytes that gets parsed and then dropped. There is a lot of allocation and deallocation, but relatively little memory that needs to remain live.

jemalloc normally manages memory at much smaller page granularity. Once allocations end up inside a 2 MiB huge page, a small amount of live data can keep the entire huge page resident. A huge page containing only one live 4 KiB object still cannot simply be returned as 4 KiB of used memory.

With enough allocation churn, that leaves a lot of mostly empty huge pages resident.

This is also why I don't think the result should be read as "THP is bad for jemalloc." This workload happens to be particularly unfriendly to it. A service dominated by larger, longer-lived allocations could behave very differently.

Arenas made it worse

THP explained most of the difference, but the default arena configuration wasn't helping.

jemalloc derives its default number of arenas from the CPU count. In this container it saw the host CPU count rather than the cgroup quota.

The host had 18 cores, so jemalloc created 72 arenas. The Tokio runtime had four worker threads.

That meant 72 arenas, each with its own dirty pages and decay state, for a process doing most of its work on four runtime threads.

Decay also depends on arena activity unless background purging is enabled. An arena used by a burst of work can therefore keep dirty pages around after that work stops touching the arena.

Why I hadn't seen it in production

The same binary had been running on the production Linux host for about twenty hours.

I checked the THP configuration there:

$ cat /sys/kernel/mm/transparent_hugepage/enabled
always [madvise] never

And then the process:

$ grep -E '^(Rss|AnonHugePages)' /proc/$pid/smaps_rollup
Rss:              137436 kB
AnonHugePages:         0 kB

Same application and workload, but no anonymous huge pages.

That explained why I had only reproduced the large RSS numbers on my laptop. The laptop test was running inside Docker Desktop's Linux VM, where THP was set to always. The production host was using madvise.

The difference between the two environments was enough to make the memory behaviour look completely different.

Configuring jemalloc

I ended up using these settings:

thp:never,narenas:4,background_thread:true,dirty_decay_ms:5000,muzzy_decay_ms:5000

thp:never makes jemalloc mark its mappings with MADV_NOHUGEPAGE. It only affects jemalloc's mappings, so there is no need to change the host-wide THP setting.

narenas:4 matches the four Tokio worker threads instead of deriving the arena count from the host's 18 cores.

background_thread:true lets jemalloc purge pages from arenas even when those arenas are no longer receiving allocations.

I also set both dirty and muzzy decay to five seconds.

For tikv-jemallocator, I put the default configuration in the binary using jemalloc's exported configuration symbol. The crate builds jemalloc with the _rjem_ prefix, so the symbol looks like this:

#[cfg(all(not(target_env = "msvc"), target_os = "linux"))]
#[used]
#[unsafe(export_name = "_rjem_malloc_conf")]
pub static MALLOC_CONF: &[u8] =
    b"thp:never,narenas:4,background_thread:true,dirty_decay_ms:5000,muzzy_decay_ms:5000\0";

#[used] is important here. Nothing in the Rust code references this symbol directly. jemalloc reads it during startup, so LTO can otherwise remove it as unused.

If you enable the crate's unprefixed_malloc_on_supported_platforms feature, that prefix is gone and the symbol has to be malloc_conf instead. Getting the name wrong is not an error. jemalloc doesn't find the symbol and runs with its defaults.

One simple way to check it is to temporarily use an invalid value like narenas:0 and watch stderr at startup:

<jemalloc>: Out-of-range conf value: narenas:0

jemalloc writes that line while parsing the configuration, so seeing it means the symbol was found. Nothing on stderr means it wasn't. You can also use tikv-jemalloc-sys to print the full allocator report:

#[cfg(target_os = "linux")]
fn print_jemalloc_report() {
    use std::ptr;
    use tikv_jemalloc_sys::malloc_stats_print;

    // Null callback writes to stderr, null options prints the whole report.
    unsafe { malloc_stats_print(None, ptr::null_mut(), ptr::null()); }
}

Then put the real value back.

I keep this configuration Linux-only. macOS doesn't have Linux THP, and the jemalloc build used here doesn't support the same background-thread setup there. Passing those options on macOS results in warnings at startup.

Operators can still override the compiled defaults with _RJEM_MALLOC_CONF.

Results

After applying the configuration:

MeasureBeforeAfter
RSS, THP always host358 MB83 MB
RSS, THP madvise host88 MB77 MB
AnonHugePages206 MB6 MB
jemalloc retained116 MB34 MB
Arena metadata11.8 MB4.8 MB
Live heap52 MB49 MB

The important part for me is that the live heap barely changed. It went from 52 MB to 49 MB.

The large change was in RSS. On the THP always host it dropped from 358 MB to 83 MB. AnonHugePages went from 206 MB to 6 MB.

The madvise host also improved, but only from 88 MB to 77 MB. That smaller difference is consistent with the arena and decay changes rather than THP.

What I took away from this

RSS alone wasn't enough to diagnose this. The kernel reported 358 MB resident while jemalloc reported only 52 MB allocated. Both numbers were correct; they were measuring different things.

If the allocator exposes its live heap size, it is worth graphing that next to RSS. A growing RSS graph doesn't necessarily mean the application is retaining objects.

I'd also check:

/sys/kernel/mm/transparent_hugepage/enabled

when memory behaviour differs between machines. In this case the production host used madvise, while Docker Desktop's VM used always. That one difference accounted for most of the discrepancy.

The other lesson for this service was not to treat jemalloc as a drop-in replacement that never needs configuration. I had switched the global allocator two releases earlier and left all of its defaults untouched. That gave a four-thread runtime 72 arenas and let the allocator's behaviour depend on the host it happened to run on.

For this workload, explicitly configuring it made a much larger difference than changing anything in the application itself.

The code is in certstream-server-rust. The allocator configuration and jemalloc metrics shipped in v1.5.5.
