HTTP/2 multiplexing vs per-connection rate limits

Every request succeeded and the log stayed 33,000 entries behind. Switching transport gave me three connections instead of one, and changed nothing.

Six Certificate Transparency logs from one operator had been falling behind for weeks on my server. There were no failed requests or rate limit responses. The worst log was about 33,000 entries behind and was fetching only 3.7 entries per second, so at that rate it wasn't going to catch up.

I suspected HTTP/2 multiplexing was the problem. The client uses reqwest, which negotiates HTTP/2 when the server supports it. Multiple concurrent requests to the same host can share a single TCP connection.

If the server applies rate limits per connection, that can be a problem. Increasing fetch concurrency doesn't help much if all of those requests still share the same connection and therefore the same limit. With HTTP/1.1, multiple in-flight requests can use multiple connections instead.

There was some reason to suspect this. The author of certspotter had run into a related issue with the same operator and worked around it by disabling keep-alives.

So I added an option to force HTTP/1.1 for selected operators. Before assuming it actually improved anything, I measured it.

Counting the connections

First I checked whether switching protocols actually changed the number of connections.

From inside the container:

$ docker exec certstream sh -c 'cat /proc/net/tcp /proc/net/tcp6' \
    | awk 'NR>1 {print $3}' | cut -d: -f1 | sort | uniq -c | sort -rn

With the default HTTP/2 transport:

# HTTP/2
1 connection -> 54.71.133.191
1 connection -> 3.137.57.126

With the affected operators forced to HTTP/1.1:

# HTTP/1.1
3 connections -> 44.231.171.103
3 connections -> 3.130.169.13

So that part behaved exactly as expected. HTTP/2 used one connection, while HTTP/1.1 used three.

If a per-connection limit was the main constraint, I expected the HTTP/1.1 run to be noticeably faster.

Measuring throughput

I ran both configurations for 25 minutes on the same machine with the same 23 logs. The only change was the HTTP version used for these operators.

The rate here is the number of entries actually fetched per second. Index jumps caused by a 400 response are excluded because those entries were not fetched.

LogHTTP/2HTTP/1.1
Sphinx2026h23.73.1
Wyvern2027h123.519.6
sphinx2027h121.020.2
Wyvern2026h20.86.1
Wyvern2027h20.00.6
sphinx2027h20.00.3
Total49.050.0

There was basically no difference.

The last two logs were already caught up and mostly idle at the tree head, which is why their rates are close to zero in both runs.

The total improved from 49.0 to 50.0 entries per second, about 2%. That is well inside the normal variation I was seeing. Sampling every 30 seconds, the busiest log varied by roughly 15 to 20% around its mean as the log's own write rate changed.

So HTTP/1.1 gave me three connections instead of one, but throughput stayed about the same.

Wyvern2026h2 looks much better under HTTP/1.1, but the runs aren't comparable for that log. It started the HTTP/1.1 run about 45,000 entries behind, while in the other run it was only about 2,400 behind. In one test it spent most of the time catching up; in the other it spent much more time idle at the head.

Checking individual requests

Since the transport change didn't make a meaningful difference, I looked at what the server was returning for each request.

The watcher asks for up to 1024 entries:

$ curl -s "https://.../ct/v1/get-entries?start=N&end=N+1023"
  attempt 1: 1.75s, 763 KB, 125 entries
  attempt 2: 1.68s, 457 KB,  77 entries
  attempt 3: 1.30s, 167 KB,  29 entries

The request asks for 1024 entries, but the server returned between 29 and 125 in these samples.

RFC 6962 allows a log to return fewer entries than requested, so this is valid behaviour. The number also changed between requests rather than stopping at one fixed entry count. That suggests the limit may be related to response size or some other dynamic server-side constraint rather than a fixed max_get_entries value.

Each request was taking around 1.3 to 1.8 seconds while returning far fewer entries than requested.

At that point, opening more TCP connections wasn't enough to materially change the result. The amount of useful data returned per request and the time each request took were much more relevant to the throughput I was seeing.

Why the HTTP/2 theory looked reasonable

The individual pieces of the original theory were real.

reqwest was using HTTP/2. The requests were sharing one TCP connection. Switching to HTTP/1.1 increased that to three connections. Per-connection throttling also exists, and another CT client had previously run into a related issue with this operator.

What I didn't have was evidence that a per-connection limit was actually the bottleneck in this case.

Counting the connections confirmed that the transport change worked, but it didn't show that the change improved throughput. Measuring entries per second did.

I've kept the HTTP/1.1 option because it is opt-in and may still be useful with a different operator or server configuration. I changed the documentation so it no longer suggests that enabling it will necessarily improve throughput.

What I would check first next time

If a client is unexpectedly slow against a remote service, I'd start by measuring how much useful data each request returns and how long the request takes.

In this case, one curl request would have shown that a request for 1024 entries could come back with only 29. That would have been useful information before changing the HTTP transport.

I'd also make sure benchmark runs start from comparable states. A log that is 45,000 entries behind behaves differently from one that is already near the tree head. That difference was large enough to make one row look like a major HTTP/1.1 improvement when it wasn't.

The per-operator HTTP/1.1 option is still available, but for these logs, on this test, changing from one connection to three did not materially improve throughput.

The code is in certstream-server-rust. The per-operator HTTP/1.1 option was contributed in #12; the measurements here are from v1.5.5.
