Reading Certificate Transparency tiles without a checkpoint

Three logs, zero errors, and 279,000 entries behind. The faster path was already there, behind an endpoint that returns 404.

Three Certificate Transparency logs from TrustAsia had been falling behind for weeks. They weren't returning errors or rate limit responses. The watcher just wasn't reading entries as fast as the logs were growing.

TrustAsia 'log2026b'   278,890 entries behind   errors: 0
TrustAsia 'log2026a'    79,392 entries behind   errors: 0
TrustAsia 'HETU2027'    37,898 entries behind   errors: 0

Every request was succeeding and the health checks were green, but the lag kept increasing.

Lag wasn't part of the health check

I ran the server against all 45 logs trusted by Chrome and Apple for two hours.

Across 45 logsCount
Reporting healthy45
Healthy and more than 5,000 entries behind19
Furthest behind, in entries1,297,126

All 45 logs were considered healthy, but 19 were more than 5,000 entries behind. The worst was more than 1.2 million entries behind.

The problem was the definition of healthy. It only told me whether requests were succeeding. It didn't tell me whether the watcher was keeping up with the log.

A watcher can fetch successfully all day while still falling further behind if its fetch rate is lower than the log's write rate.

I added lag as its own metric. That made the problem visible, but I still needed to figure out why these particular logs were so slow.

Two ways to read a CT log

The RFC 6962 interface uses get-entries. You request a range of indices and the log returns JSON.

The newer static-ct-api works differently. Entries are stored in data tiles of 256 entries at fixed paths. A signed checkpoint normally provides the current tree size. Because the entry data is served as static files, it can sit behind a CDN.

These three TrustAsia logs are listed as RFC 6962 logs, but they also expose static-ct-api tiles. I found out about that after Effy Elden opened an issue and pointed to a ct-policy discussion where the operator confirmed that the tiles were intentional.

I compared both paths for the same 256 entries near the head:

PathTransferredTime
/tile/data/x010/x076/918189 KB5.96s cold, 0.36s warm
get-entries?start=…&end=…696 KB30.4s / 30.7s / 25.2s

A warm tile took 0.36 seconds. The same entries through get-entries took between 25 and 31 seconds.

The tile response was also much smaller because it was compressed.

The same operator has another log that publishes a checkpoint, and my server was already reading that one through tiles. It was only 1,310 entries behind while the other three were between roughly 38,000 and 279,000 behind.

The missing checkpoint

Normally a static-CT client starts by fetching /checkpoint. The checkpoint provides the tree size and can be verified before the client starts fetching tiles.

These logs return 404 for /checkpoint.

My tile watcher required a checkpoint, so it couldn't use the tiles even though the tile data itself was available.

The logs do publish their tree size through the RFC 6962 get-sth endpoint.

So I added an option to use get-sth as the source of the tree size while still fetching the actual entries from tiles:

static_logs:
  - name: "TrustAsia log2026a"
    url: "https://ct2026-a.trustasia.com/log2026a"
    expected_log_id: "dNudWPfUfp39eHoWKpkcGM9pjafHKZGMmhiwRQ26RLw="
    tree_size_source: get_sth

That was enough to make the basic approach work, but running it against the real logs exposed a few cases I hadn't accounted for.

get-sth can move backwards

Soon after starting, one watcher stopped making progress because the tree size returned by get-sth was slightly lower than a value it had returned earlier.

For a signed static-CT checkpoint, a decreasing tree size is something worth treating seriously. My existing code marked the log unhealthy and backed off.

That behaviour didn't work well with get-sth.

The endpoint is served by multiple replicas, and those replicas can be a few entries apart near the head. One request can therefore return a slightly smaller tree than the previous request.

I changed the get-sth path so that a regression is counted as a metric and re-polled instead of immediately affecting log health. The watcher still never fetches beyond the tree size reported by the log.

The high water mark had the same problem

The watcher also kept the largest tree size it had ever seen.

With multiple replicas behind the endpoint, that value eventually comes from whichever replica happens to be furthest ahead. Requests that later hit another replica then appear to be regressions.

That can leave the watcher waiting for the other replicas to catch up to a value returned by one replica earlier.

The assumption made sense for a checkpoint, but not for a load-balanced get-sth endpoint.

No checkpoint also means no guaranteed partial tiles

There was another difference at the head of the log.

The static-ct-api specification requires partial tiles, such as .p/<W>, for tree sizes that have a published checkpoint. These logs don't publish checkpoints, and they don't serve partial tiles.

Requesting one returns 404.

So when the tree size comes from get-sth, I floor it to the last complete 256-entry tile.

That means the newest 0 to 255 entries aren't available through this path until their tile fills. For a high-volume stream this usually adds only a small amount of latency, but it matters if you're using the stream to watch for a specific certificate as soon as it appears.

Increasing concurrency

After those changes, one of the three logs still couldn't keep up.

Near the head, tile requests were taking roughly 20 seconds and arriving in groups of four. The watcher had four in-flight tile requests.

The difference between catch-up and the head turned out to matter here. Old tiles are likely to already be in the CDN cache. Newly created tiles near the head often aren't, so those requests have to reach the origin.

The 0.36 second result from earlier was a warm cache hit. Near the head, requests could be much slower.

I increased the number of in-flight tile fetches from 4 to 16. Aggregate throughput across the three logs went from about 50 entries per second to 276.

TrustAsia 'log2026a'79,3920

Two logs caught up completely and the third started closing its backlog.

The verification tradeoff

Using tiles this way gives up an important property of the normal static-CT protocol.

There is no checkpoint, so there is no signed static-CT tree head to verify the tiles against.

The get-sth signature doesn't solve that either. These tiles include the static-CT leaf_index extension in their TimestampedEntry, so re-encoding a tile entry doesn't produce the RFC 6962 Merkle leaf hash needed to verify it against the get-sth tree.

The author of certspotter looked at the same logs and chose not to support them for this reason. That makes sense for a tool doing cryptographic CT monitoring.

My server has a different job. It streams certificates to downstream consumers and doesn't verify inclusion proofs today. For that use case, I decided to allow this mode as an explicit option. It is logged at startup and documented as unverified.

I wouldn't use the same approach in a CT monitor that depends on cryptographic verification.

What changed

There were two separate problems here.

The first was monitoring. Successful requests didn't mean the watcher was keeping up, so lag needed to be measured directly.

The second was how these particular logs were being read. get-entries was too slow to keep up, while the same entry data was available through static tiles. Using the tree size from get-sth made those tiles usable even without a checkpoint, with the verification limitation described above.

Running it against the live logs also exposed assumptions that weren't obvious from tests: get-sth responses from different replicas can move backwards slightly, a high water mark doesn't work well across those replicas, and logs without checkpoints don't have to provide partial tiles.

For clients that talk to external distributed systems, those details are worth testing against the actual service rather than only against a local implementation.

The changes are in certstream-server-rust v1.5.5. The behaviour of these logs was originally reported and measured by Effy Elden in issue #14.
